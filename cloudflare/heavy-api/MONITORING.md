# Cloudflare read-only API monitor

## G618 Cloudflare baseline

`scripts/verify-g618-scale-ops-baseline.mjs` emits `heavy-chain.g618.scale-ops-baseline.v2` and the release validator consumes the matching `production-monitor.v2` evidence. Before building or starting the local performance fixture it requires an explicit HTTPS API origin and brand via `--apiBaseUrl` / `--brandId` (or monitor environment variables), plus a live `HEAVY_CHAIN_MONITOR_TOKEN`. The existing 96-hour baseline minimum, local large Gallery/Canvas fixture and preview cleanup checks remain. Missing/invalid route timings no longer default to zero. The runner records its explicit scope/window/failure threshold/sample-size expectations and sends the same values to the monitor.

The v2 evidence check validates fresh matching origin/brand/window, the limited principal-sample coverage, nonempty completed jobs and internally consistent counters, zero failed/stale jobs, unique readable private-image samples with verified checksums, and current-month brand AI estimates/quota. Warnings, uncertain estimates, disabled AI, missing fields, unknown/null failure rates, stale or foreign observations fail. Old Edge-run, signed-URL and known-probe-failure exemptions are removed. Reports explicitly retain `businessCompletion:not_verified` and unverified production concurrency, Worker CPU, provider invoices, fleet SLO and browser business workflows. Passing this bounded baseline is not proof that old services were retired, that the Cloudflare migration is complete, or that real production business workflows completed. The focused checks are local-only; no production baseline, inference or deployment was performed.

## Offline workspace evidence consistency

`npm run verify:workspace-readback -- --readback <fresh-v2-report.json> --expectations <expected-run.json>` checks the collector's v2 evidence. The expectations file must specify `apiOrigin` (exact HTTPS origin), `brandId`, `userId`, `since` and `jobs:[{id,requestId,candidateCount,protectedEdit}]`. Derive these from the intended run, not the observed subset. Candidate count is 1–4; protectedEdit is an explicit boolean. The report must have been captured within 15 minutes, match the precise scope, include completed requested jobs and every expected candidate phase, and verify private image checksums. Protected edits additionally require exact canonical final-save links and completed final jobs. Duplicate, foreign, unexpected, partial and unknown records fail. No legacy cleanup/release/workspace flags may be mixed with this mode.

This is offline consistency, not authentication of a supplied JSON file, independent live proof, visual quality, Gallery/Canvas/History/Jobs reuse, billing/CPU/load evidence or business closeout. Successful output is `persistedEvidenceConsistent:true`, with `businessCompletion:not_verified`. It does not delete saved images or require fabricated old Edge telemetry. The legacy no-expectations path remains for historical reports only. No production invocation was performed during implementation. Focused verifier tests: 4; collector tests: 8.

## Cloudflare image QA runner

The historical `hc-10m-real-generation-qa.mjs` filename now runs only the Cloudflare API. `npm run qa:cloudflare-image -- --apiBaseUrl <HTTPS-API-origin> --brandId <brand> --requestId <UUID>` observes an existing request. `HEAVY_CHAIN_MONITOR_TOKEN` is a live consumer-auth token supplied outside command arguments. There are no default user/brand IDs, provider keys, old environment-file loads, automatic enqueue, polling loop or data deletion.

A new inference uses the explicit `qa:cloudflare-image:submit` command with the same scope options plus `--action generate-image|edit-image|model-matrix --input <JSON-file>`. The file must contain the actual intended API body, matching brandId and rightsConfirmed:true; the runner never invents consent. This command is not permission to enable a disabled model, spend outside approval, bypass verification or perform cleanup. Inputs and user approval still govern which scenarios may run. Hardcoded old multi-provider scenario sweeps and cleanup modes are retired.

The runner verifies the current profile and reads the same request first. Only a definite image_request_not_found404 with no prior local attempt allows a POST. Before sending, it exclusively creates a0600 attempt.json, fsyncs file/directory and reads it back. The record binds origin/brand/user/request/action/canonical payload hash, not tokens or image input bytes. A competing write, disk failure, mismatching record or unreadable record stops submission. Once the record exists, a crash-before-send, timeout or absent receipt cannot trigger another POST. Keep this directory intact across processes; deleting/copying state or losing the disk is not a safe retry mechanism. Readback may reconcile already-stored persistence through the API, but never requests reinference. An existing remote request without a local input binding is not adopted as a successful new submit; use explicit readback to inspect it.

The POST response is not completion proof: the runner fetches the same receipt again and checks current job owner/brand, exact candidate IDs/indexes/count, every expected ledger phase, final-image identity and actual private bytes/recorded hashes via the workspace collector. Partial/unknown states remain unverified. Protected edits still need the existing browser compositor and final-save flow; raw candidate success alone cannot pass. A successful persistence result still leaves visual quality and business completion unverified. Signed URLs, raw request bodies and arbitrary receipt metadata are not written to the report.

Local verification: QA6 tests cover readback-only default, lost-response single POST, missing/changed authority, disk failure, recorded-404 no replay, unbound existing request, candidate mismatch, unknown/partial/protected states, and actual exclusive0600 journal reopen/overwrite rejection. Monitor6/collector8 passed in the combined pre-final-journal run; final QA6 and frontend typecheck/help/diff checks pass. No real inference, token acquisition, old data copy or deletion occurred. Root package.json/package-lock.json no longer declare Supabase JS or its dependency subtree (lock-only update, no unrelated version changes). Existing node_modules/cache bytes and archived Supabase/Deno sources are not removed by this dependency edit; actual full-network-zero and final service cleanup remain unverified.

## Exact workspace collector

`npm run workspace:collect-readback -- --apiBaseUrl https://heavy-chain-api.nichika2000823.workers.dev --brandId <brand-id> --jobIds <job-id>,<job-id> --since <ISO-time> --out <report-file>` uses the same live `HEAVY_CHAIN_MONITOR_TOKEN` environment variable. No default identities, old DB credentials or broad timestamp-based telemetry matching. At most100 distinct named jobs, each with up to10000 images through job-filtered pagination. The since boundary is mandatory. Names/versions in source metadata are declared inputs; actual execution steps come only from the scoped D1 execution endpoint, with unknown/not-started states retained. No synthetic completion is derived from declared task codes.

The v2 collector checks exact job/brand/user/time relationships and each returned final image's private bytes, plus recorded checksums where available. Report projection omits raw prompts, input bodies, signed URLs and unrelated metadata; known session-token occurrences cause output refusal. `collectionComplete` means evidence collection, not successful execution or business completion. Empty images, absent ledger records, foreign/malformed rows, capped or duplicated pages and content failures remain incomplete. Missing checksum metadata is labelled unverified, not invented.

Protected source jobs may contain only hidden intermediate images while final images belong to separate final-save jobs. The collector now follows only completed final-save phases from the execution ledger. It reads the exact image and final job, rechecks owner/brand/time, canonical image/job/path identity, sourceJobId, request/candidate identity, completed status and the final job's recorded checksum/size against actual private bytes. Verified links are explicit in canonicalFinalLinks; raw metadata aliases and intermediate phases never initiate discovery. Unstarted/unknown final saves are recorded without being fetched or replayed. Content failures or invalid linkage stay incomplete. The old closeout verifier's v2 acceptance contract remains unfinished; it explicitly rejects v2 instead of interpreting missing old telemetry as successful proof.

`npm run monitor:production -- --apiBaseUrl https://heavy-chain-api.nichika2000823.workers.dev --brandId <current-brand-id>`

Requires `HEAVY_CHAIN_MONITOR_TOKEN` containing a live, verified consumer-auth session token. Do not pass the token on the command line or paste it into reports. The script never loads old environment files, logs in, refreshes a token, grants a role, or uses a service-role key. API and brand may alternatively be explicitly configured with `HEAVY_CHAIN_MONITOR_API_URL` and `HEAVY_CHAIN_MONITOR_BRAND_ID`. There is no default account or brand. `--help` performs no network access.

The v2 JSON report covers current-principal/current-brand jobs and generated images, plus the brand's authorized monthly AI usage summary. It is not a platform-wide administrator monitor. All requests are GET, reject redirects, have15-second deadlines and bounded bodies; there is no retry, inference, reconciliation, signed-URL creation, or cleanup of production data. Private media is read through the owner-scoped content endpoint, with SHA-256 and byte-count matching when metadata records them. A readable object without a recorded checksum is explicitly not checksum-verified. This does not assess decoded image quality.

Defaults:24-hour job/image window,20-minute stale threshold,5000-row observation cap,20-image sample, failure-rate ceiling0.15, zero failed jobs/stale jobs/storage errors allowed. Numeric controls are explicit CLI options; maxRows must be a multiple of100 and at most10000. Empty job/media evidence, truncated/duplicate pagination, foreign brand rows, malformed responses, unknown job state and uncertain AI candidates cannot pass. Pagination is an offset-based, nontransactional observation, not an atomic database snapshot. Sampling only proves the sampled objects at observation time.

Output: `summary.json` in the explicit `--out` directory or a timestamped `output/cloudflare-monitor-*` directory; exit0 means this API observation met its declared thresholds, not release/E2E completion. The report separates estimated usage from invoice/free-allocation data and leaves UI, CPU, billing and business completion unverified. `--skip-ui` remains accepted for old callers, but v2 never starts a browser. Use the task's selected browser surface separately for authenticated UI evidence.

The current G618 scale gate accepts only the v2 bounded contract: the runner's local 1200-image/600-Canvas safety checks plus explicit current-principal Cloudflare monitor evidence. It rejects historical v1 Edge Function/usage-event/signed-URL artifacts and never treats absent telemetry as zero failures. This gate does not establish old-service retirement, migration completion, fleet-wide load/CPU/billing evidence, browser business-workflow completion, or business closeout; historical artifacts remain available for audit and are not deleted or moved. The remaining legacy collector and real-generation QA scripts still require separate migration; this change alone does not permit removal of the root SDK dependency.
